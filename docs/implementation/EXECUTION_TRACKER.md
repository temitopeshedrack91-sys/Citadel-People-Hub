### Confirmed source findings and report corrections

1. **Supabase remains high risk.** The prior read-only metadata findings describe broad browser grants, permissive policies, public storage buckets, and callable role-registration functions. The local candidate migration only addresses profile/Auth registration and remains unapplied and untested. It is not evidence that production RLS or Storage is fixed.
2. **The canonical database target is only partly established.** Frontend Supabase configuration identifies Citadel (`czbwedtrnzlfpdbzlnim`); `backend/.env.example` points elsewhere and the deployed Laravel database target is unverified. The live schema and Laravel model are not interchangeable (including text versus numeric task identifiers). Do not auto-link identities by email.
3. **Auth changes are partial.** When Laravel is configured, the frontend signs in through Sanctum and restores the stored token through `/auth/user`; local preset personas are restricted to an explicit development-only opt-in. Supabase signup no longer sends a role or calls `register_user`, and Supabase-only role resolution reads `profiles`. However, the candidate SQL that would enforce the low-privilege trigger/profile policy has not been run; production registration RPC grants/policies are unchanged. Sanctum is configured with 60-minute token expiration, and no refresh endpoint/flow was found. The bearer token is stored in browser local storage. Also, `LoginModal.tsx` declares demo credential data outside its `import.meta.env.DEV` guard; its UI and persona switch are gated, but production bundle exclusion still needs verification.
4. **RBAC documentation overstates centralization.** The UI has navigation/route guards and `src/utils/rbac.ts`; `authorizeApiRequest` has no call sites outside its own module/tests. Laravel performs separate controller role checks. The frontend maps `BUSINESS_HEAD` and `DEPARTMENT_HEAD` to the same `HR_STAFF` role, while backend scope decisions distinguish them. Therefore the RBAC contract is not yet aligned end-to-end.
5. **Some security fixes are already in the working tree and should not be repeated.** `TaskProjectAccess` scopes project/task collections and objects and constrains relationships; the leave-balance routes now scope by employee/entity/department. Regression tests exist for these changes. They are still uncommitted and require the Stage 4 regression run.
6. **Talent is not end-to-end persistent.** `TalentController` exposes only journey list, task completion patch, and requisition list. There are no requisition create/update/status, candidate, onboarding create, checklist-template, document-submission, orientation, task-create, or reminder routes. The existing requisition model/table has `requisition_data` JSON; onboarding has `journey_data` JSON; no Laravel Candidate model/table or checklist-template persistence was found. Talent role gates also do not match the RBAC contract: list endpoints allow PCCM/business/department heads, while task completion allows only PCCM/department heads, excluding other roles the contract calls Admin/HR Staff. Laravel repository methods call absent paths and catch errors, then mutate static mock arrays or return success/no-op. Talent views also restore demo arrays on failed/empty API reads. Error states therefore can be shown as apparent demo records or successful actions.
7. **Fallbacks are broader than Talent.** `LaravelEmployeeRepository` and multiple `LaravelPayrollRepository` read/write methods also return/mutate static seed arrays after API failure. This conflicts with the production requirement not to mask API errors. Exact locations are listed in the matrix.
8. **Attendance import is a working client-side parser/matcher, not a persisted server workflow.** It keeps raw punches, deduplicates using staff/device identity and timestamp, and computes local-date first/last-punch summaries in local storage. Laravel provides clock-in/out sessions and summaries only; there are no shift, import, reconciliation, or correction routes/models. The Attendance view displays a 10-minute grace period and schedule examples, but the backend does not calculate shifts, lateness, breaks, overtime, or payroll effects. Preserve the importer and its current export assumptions while establishing authoritative policy inputs.
9. **Leave approval and basic payroll already exist.** Leave has staged approval history and the current implementation scopes balance reads, but trusts client `totalDays` and has no policy-driven day calculation, overlap handling, transaction ledger/accrual, or cancellation reversal. Payroll already calculates configured salary components, allowances, bonuses, deductions, loans, and provident fund and has a draft/finalize flow. A unique database constraint already exists on `(pay_frequency, period_start, period_end)`; older report language saying uniqueness is unconfirmed is stale. Immutable rule/input snapshots, explicit review/approval stages, statutory rule versions, attendance/unpaid-leave inputs, and confirmed policy rules remain absent.
10. **Other end-to-end gaps remain.** Profile edits are local-storage-only; notification read operations exist but domain notification creation/reminders and scheduler work are absent. The Reports view reads repositories and computes/export statistics in the browser; no dedicated reports API was found. Recruitment “View All Candidates” is an alert, not a workflow. No dedicated Talent API tests or browser E2E runner are present in the inspected test inventory.
11. **NotchHR evidence boundary:** public official materials advertise HR modules and employee self-service, but no authenticated backend operation, schema, authorization behavior, or business rule was observable. The owner previously confirmed no demo access. The current public comparison is documented in `notchhr-product-analysis.md`; do not present vendor marketing as verified behavior.
